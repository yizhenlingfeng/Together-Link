## 1. 结论摘要

| 项目 | 结论 |
|---|---|
| 目标 | 同一套代码、两个构建产物：`together-link-2.0-1.20.1.jar` 与 `together-link-2.0-1.20.4.jar`，功能对等 |
| 推荐路线 | **单仓库 + Gradle 版本参数（`-Pmcver`）先行**；版本差异文件超过阈值后再拆双 Loom 子工程 |
| 关键前提 | 必须先拿到可用的 **BBS 2.7-1.20.4**（1.20.1 侧目前用的是本地 2.7，公开 1.20.4 最新只有 2.3.3） |
| 最大风险 | 53 个 Mixin 深入 BBS 内部类；开发环境能启动不代表生产 remap jar 能启动，必须两种都测 |
| 预估工作量 | **13–23 人日**，单人约 2.5–3 周；两人并行可压到 1.5–2 周 |
| 关键路径 | M0 → M1 → M2 → M3 → M4 → M5 → M6 → M8 |
| 是否改代码 | 本阶段否；确认计划后才进入 M1 |

**一句话**：先解决 BBS 1.20.4 依赖，再把构建参数化，然后按“编译 → Mixin → 开发客户端 → 生产客户端 → 双端联调 → 1.20.1 回归”的顺序推进；不要一上来就复制分支。

### 2.3 已知问题（必须在双版本计划中一并处理）

1. **BBS 版本错位**：本地 1.20.1 用 2.7，但 Modrinth 上 1.20.4 最新公开版是 2.3.3。若 1.20.4 用户只装公开版，2.7 编译出的 addon 很可能因内部类/方法差异而崩。
2. **refmap 陈旧**：`client-bbs-together-refmap.json` 是旧文件；开发环境（named mappings）能跑，生产 jar（intermediary）可能才暴露 Mixin 注入失败。
3. **开发运行目录混用**：当前 `run/` 同时承载 1.20.1 客户端/服务端；1.20.4 必须使用独立 `run-1.20.4/`，否则 world、BBS 配置、按键、缓存会互相污染。
4. **BBS 传递依赖被排除**：`transitive = false` 让开发客户端没有 Sodium/Iris，BBS 对它们的 Mixin 会跳过并告警；1.20.4 要确认这是否仍可接受。

## 4. 前置条件与决策门（Gate）

| 编号 | 决策/前提 | 判定标准 | 不满足时的处理 |
|---|---|---|---|
| **G0** | 可构建的 BBS 2.7-1.20.4 | `~/.m2/repository/mchorse/bbs/2.7-1.20.4/` 存在，jar 的 `fabric.mod.json` 声明 `=1.20.4`，`api/bbs-api.txt` 与 1.20.1 差异可接受 | **停止 M2 之后的开发**；先单独立项把 BBS 2.7 移植到 1.20.4，或把 addon 降到公开 2.3.3（需重做 Mixin 审计） |
| **G1** | 1.20.4 首编译的版本差异可控 | 版本专属文件 ≤ 10 个、差异代码 ≤ 500 行 | 超过则改用双 Loom 子工程，必要时引入预处理器 |
| **G2** | Mixin 修复成本可控 | 53 个中失败 ≤ 5 个，且均有明确替代注入点 | 超过则重新评估 1.20.4 支持范围，或先做“无 Mixin 降级版” |
| **G3** | 生产 jar 可启动 | 开发客户端与生产 remap jar 均无 `Mixin apply failed` / `InjectionException` | 不算完成，禁止发版 |
| **G4** | 1.20.1 无回归 | 原有验收清单关键项全绿 | 回滚 1.20.4 变更，先保 1.20.1 |

**建议先确认 G0**：BBS 1.20.4 的 2.7 源码/分支在哪里、能否 `publishToMavenLocal`。这是整个计划的地基，地基不成立，后面的排期都只是纸面数字。

## 5. 方案对比

| 方案 | 做法 | 优点 | 缺点 | 适用 |
|---|---|---|---|---|
| **A. 双分支** | `1.20.1` 与 `1.20.4` 两个长期分支 | 隔离彻底，首版最快 | 每修一个 bug 要 cherry-pick 两次；历史容易分叉 | 只做一次性移植，不推荐长期 |
| **B. 单工程 + 版本参数（推荐先行）** | `-Pmcver=1.20.1/1.20.4` 切换依赖；共享 `src/`，版本差异放 `src/versions/<mc>/` | 改动最小，保留现有 IDE/运行配置；一套代码 | 同一工作区来回切换会重跑 Loom 配置；不能真正并行构建 | 版本差异 ≤ 10 个文件 |
| **C. 双 Loom 子工程（推荐长期）** | `:v1_20_1`、`:v1_20_4` 两个子工程共享 `src/` 与 `versions/` | 缓存独立、可并行 CI、IDE 可同时打开 | 需要重构 `settings.gradle` / 目录，约多 1 人日 | 版本差异变大或要并行发版 |
| **D. 预处理器** | ReplayMod Preprocessor，单源码内 `//#if MC >= 12004` | 适合大量零散差异 | 工具链、IDE 高亮、调试都变复杂 | 差异散落在几十个共享类里才考虑 |

**推荐**：**B 起步，G1 不通过再升 C**。理由：

- 当前 1.20.4 的主要差异预计集中在构建配置、少量 vanilla API、以及 BBS 内部方法签名，不需要一上来就重构目录。
- 53 个 Mixin 的修复更适合在单一源码树里逐个处理，双工程会让“改一处、两边验证”变慢。
- 等版本专属文件真的超过 10 个，再拆 C，迁移成本仍然可控。

**Mixin 审计要点**：

- 43 个客户端 Mixin 里有 9 个注入 `render`、5 个注入 `<init>`，这两类最容易因 1.20.4 渲染/初始化流程变化而失效。
- 主端 `ModelBlockEntityMixin`、`ServerNetworkBbsOpMixin`、`PacketCrusherBoundsMixin` 涉及网络包与方块实体，1.20.4 的包构造/编解码若有变化会直接崩。
- 所有 `remap = false` 的 BBS 目标不需要映射，但**目标方法名/描述符仍可能变**；`remap` 默认的 vanilla 目标（`ClientPlayerInteractionManager`）还要经过 Yarn 映射变化。
- 生产环境必须验证，因为开发环境是 named mappings，refmap 错误会被掩盖。

## 12. 本计划明确不做的事

### 15.5 模型方块面板 UI 消失修复（2026-10-22）

**症状**：1.20.4 首次进入游戏后打开“模型方块”面板，界面 UI 不显示，但点击原按钮所在区域仍能触发按钮。

**定位**：`UIModelBlockPanelBbsOpMixin` 在 `render()` 的 TAIL 中首次调用 `ensureShieldsAttached()`，会向面板动态 `add()` 三个点击护盾；同时 `refresh()` 里的 `scrollView.resize()` 也在渲染遍历中执行。1.20.1 能容忍这种“渲染中改 UI 树/布局”，1.20.4 下会让面板布局处于半更新状态，表现为 UI 消失但命中测试仍按旧坐标工作。

**修复**：
- 点击护盾改到 `<init>` TAIL 一次性挂载；
- 锁定区刷新改到 `fill()` TAIL（选择方块时）和 `<init>` TAIL；
- `render()` 只保留 `pickEdit` 状态切换和半透明遮罩绘制，不再增删子元素或调用 `resize()`。

**验证**：1.20.4 客户端启动、dashboard 的 `model blocks` 面板构建正常（31 ms），无 Mixin 错误；仍需在游戏内实际打开面板确认 UI 恢复。若仍复现，需要 BBS-only（不装 Together）对照，以判断是否为 BBS 2.7-1.20.4 自身的 stencil/framebuffer 问题。

### 15.6 合并为单个通用 jar（2026-10-22）

**目标**：不再分 1.20.1 / 1.20.4 两个发布产物，只产出一个 `together-link-2.0.1-1.20.1-1.20.4.jar`。

**做法**：以 1.20.1 为编译基线，把 1.20.4 的差异收敛到运行时兼容层：

| 差异 | 单 jar 处理 |
|---|---|
| `GameOptions.debugEnabled`（1.20.1） / `DebugHud.shouldShowDebugHud()`（1.20.4） | `ClientCompat.isDebugHudVisible()` 反射探测，不再直接链接任一 API |
| `PlayerListEntry.getSkinTexture()`（1.20.1） / `getSkinTextures().texture()`（1.20.4） | `ClientCompat.skinTexture()` 反射探测 |
| `ModelBlock.getPickStack` 参数 `BlockView` / `WorldView` | 不再注入该方法；改注入 `MinecraftClient.doItemPick()`，该方法两版都是 `method_1511`、无参数 |
| `PacketByteBuf.writeNbt(NbtCompound)`（1.20.1） / `writeNbt(NbtElement)`（1.20.4） | `ModelBlockPacketGuard` 改用稳定的 `NbtCompound.write(DataOutput)` 计算 NBT 体积 |
| `fabric.mod.json` 版本范围 | `minecraft: >=1.20.1 <=1.20.4`，`bbs: >=2.6` |

**构建**：
- 默认 `gradlew build` 产出通用构建产物，编译基线 1.20.1，`version = 2.0.1-1.20.1-1.20.4`；
- `-Pmcver=1.20.4` 保留为编译/运行验证目标，产物名带 `-verify`，不作为发布物。

**验证**：
- 1.20.1 开发客户端：加载 `bbs_together 2.0.1-1.20.1-1.20.4`，进入世界，dashboard 面板正常，无 Mixin 错误；
- 1.20.4 **生产环境**（Fabric Loader 0.19.3 + Fabric API 0.97.3 + BBS 2.7-1.20.4）：加载同一个通用构建产物，进入含模型方块的世界，连续运行约 90 秒，无 `NoSuchMethodError` / Mixin 错误；
- 期间发现并修复了 `ModelBlockPacketGuard` 的 `PacketByteBuf.writeNbt` 二进制不兼容；修复后同一世界不再崩溃。

**产物**：
`build/libs/together-link-2.0.1-1.20.1-1.20.4.jar`

**注意**：
- 通用 jar 不是“1.20.1 与 1.20.4 客户端互连”；两个版本的客户端/服务端仍各自配套。
- 1.20.4 仍需 BBS `2.7-1.20.4`；公开 BBS 2.3.3 不满足 `>=2.6`。
- 若后续再调用 1.20.1/1.20.4 签名不同的 vanilla API，优先走 `ClientCompat` 反射或改用两版稳定的上游方法。
